# Vercel Deployment Readiness Audit

**Audit date:** 2026-10-12  
**Scope:** Existing Vite/React frontend, Express/Mongoose backend, MongoDB and connected services. Read-only application/config review; this report is the only file added. No packages were installed, environment values were invented, or deployment/GitHub actions taken.

## Verdict

**NOT READY for a complete production deployment on Vercel.** Vercel currently documents support for Express applications as Functions, so the API is not inherently incompatible. The current application nevertheless serves uploaded files from a local directory, which is not durable or statically served by Vercel Functions; the configured 5 MiB upload ceiling also exceeds Vercel's 4.5 MB Function request-body limit. Production URLs, secrets, database access and storage settings are not present to validate. The frontend and backend can be configured as separate Vercel projects, but deployment would not preserve the current media behavior without remediation. See [Express on Vercel](https://vercel.com/docs/frameworks/backend/express), [Function limits](https://vercel.com/docs/functions/limitations), and [Function runtimes](https://vercel.com/docs/functions/runtimes).

## Findings

### Blockers

1. **Local media is incompatible with Vercel Function filesystem semantics.** `backend/src/app.js` mounts `/uploads` through `express.static(getLocalStorageDirectory())`, while `backend/src/utils/storage.js` writes to local disk when `STORAGE_PROVIDER=local`. The Vercel Express integration does not serve `express.static()` assets, and Function filesystems are read-only other than temporary `/tmp` storage. New uploads and existing local media will therefore not behave as durable, publicly accessible media. Configure durable object storage (the existing S3 path is a candidate), migrate the existing 68 local upload files and their media records/URLs, and verify retrieval before switching traffic. Keep those user uploads; do not put them in the Git repository. See [Express on Vercel](https://vercel.com/docs/frameworks/backend/express) and [Function runtimes](https://vercel.com/docs/functions/runtimes).
2. **Upload maximum exceeds Vercel's request limit.** `backend/src/middlewares/upload.js` accepts files up to 5 MiB, but Vercel Functions limit request and response bodies to 4.5 MB. Multipart overhead can make the effective file limit lower still. Lower the app limit with a clearly documented user-facing value or, preferably for larger media, implement a direct-to-object-storage upload flow. See [Vercel Function limits](https://vercel.com/docs/functions/limitations).
3. **Production configuration cannot be verified or supplied from this repository.** There are no real production URLs or `.env` files to audit. `frontend/scripts/validate-production-env.js` requires real HTTPS `VITE_API_URL` (ending in `/api`) and `VITE_SITE_URL`; backend production checks require a real non-local `MONGO_URI`, production JWT secrets, and valid HTTPS origins. These values must be supplied privately in the appropriate Vercel project's environment settings. Never expose backend secrets as `VITE_*` values. Vercel environment changes apply to new deployments. See [Vercel environment variables](https://vercel.com/docs/environment-variables).

### Important risks

- **Rate limits are instance-local.** `backend/src/middlewares/rateLimiters.js` uses the default in-memory `express-rate-limit` store, and AI concurrency uses a module-level counter in `backend/src/services/portfolioAiService.js`. They do not coordinate across serverless instances and are not a global abuse or AI-spend ceiling. Use a shared store or provider-side controls before exposing sensitive/costly endpoints publicly.
- **MongoDB connection and startup remain unverified.** `backend/src/config/database.js` connects before `app.listen()` and calls `process.exit(1)` on connection failure. A reused module/Mongoose connection may help warm invocations, but no Vercel cold-start, concurrency, timeout, or reconnection test was run. Configure Atlas with a least-privilege app user, region-aware placement, and an appropriately restricted network path; do not allow `0.0.0.0/0` by default. Atlas requires a network access path from the app; see [MongoDB Atlas connectivity](https://www.mongodb.com/docs/atlas/connect-to-database-deployment/).
- **Refresh cookies require real-domain browser testing.** The frontend uses `withCredentials`, the API uses credentialed CORS with exact origins, and refresh tokens are in an HTTP-only cookie. `SameSite=None; Secure` is set in production, but default frontend/API hostnames on separate registrable domains can be treated as third-party cookies and blocked by browsers. Prefer related custom domains and test login, refresh, and logout in browsers with third-party cookies restricted.
- **Security header policy needs an explicit review.** `backend/src/app.js` disables Helmet's Content Security Policy. That may be intentional for this API, but should be recorded and validated against the frontend/API threat model before production.
- **Two-project setup differs from the current deployment guide.** `docs/deployment-guide.md` documents Vercel frontend + Render backend. For Vercel-only hosting, create distinct projects with root directories `frontend` and `backend`; use the frontend's existing `vercel.json` SPA rewrite. Vercel's current Express docs recognize Express entrypoints and port-listener applications. Confirm framework detection/build settings on a non-production preview rather than adding an adapter preemptively.
